ai-core 模块

给 GEC6818 + LVGL 嵌入式项目加上原生 Function Calling 能力的独立 C 模块。模型（Qwen2.5:7b）通过 Ollama API 输出标准 tool_calls JSON，C 代码解析后调用注册的硬件 handler，实现"自然语言 → 控制板载硬件"的完整闭环。

这是什么

一个不依赖 LVGL 的 AI Agent C 模块，封装了：

  • 与 Ollama HTTP /api/chat 的通信
  • Qwen2.5:7b 原生 Function Calling（tool_calls）的解析与分发
  • 工具注册表（数据驱动，新增硬件零成本）
  • 事件回调机制（让 UI 层负责线程安全，自己不碰 LVGL）

跑通后，你可以对开发板说"帮我点亮 2 号 LED"，模型会输出 control_led({"led_id":2,"state":"on"})，C 代码自动执行硬件控制并把结果回传，模型再生成自然语言回复。

验证过的最小闭环： 用户输入 → 模型决定调工具 → 执行硬件控制 → 结果回传模型 → 生成自然语言回复。三个用例全部跑通。

快速开始（PC 测试）

准备依赖

WSL2 Ubuntu 上 sudo apt install build-essential，进入 ai-core 目录执行 make get_cjson 下载 cJSON 单文件库。

启动 Ollama（关键）

Windows PowerShell 设 set OLLAMA_HOST=0.0.0.0 后 ollama serve，必须监听 0.0.0.0 才能让 WSL2 访问。

获取 Windows IP

WSL2 执行 cat /etc/resolv.conf | grep nameserver，拿到类似 172.28.80.1 的 IP，改到 main_test.c 顶部的 host 变量。

编译运行

执行 make 编译 PC 测试版，再 make run 直接跑。

测试用例

依次输入："你好" / "帮我点亮 1 号 LED" / "查看温度" / "蜂鸣器响 1 秒"，观察是否触发 [工具调用] 和 [MOCK ...] 输出。

验证通过标志： 看到 [工具调用] control_led({"led_id":1,"state":"on"}) + [MOCK hw_led_set] LED 1 -> ON + [最终回答] 三段都出现，说明 FC 闭环完全跑通。

核心机制

1. Function Calling 闭环（最重要）

代码位置：ai_agent.c 的 worker_thread() 函数。

2. 工具注册表（数据驱动）

新增一个硬件工具只需要两步：写 handler 函数，在 g_tools[] 加一行。模型通过自动生成的 tools JSON Schema 知道有哪些工具可用。

3. 事件回调（解耦 LVGL）

Agent 不直接调用任何 LVGL 函数，而是发事件：

事件类型触发时机字段
AI_EVT_THINKING模型输出思考块text
AI_EVT_ACTION工具被调用tool, args, result
AI_EVT_ANSWER模型最终回复text
AI_EVT_ERROR出错text
AI_EVT_DONE一次请求完全结束（无）

4. PC / 板子双版本硬件控制

ai_tools.c 用 #ifdef __PC_TEST__ 切换：PC 测试 make 默认带这个宏走 printf mock；板子部署 make arm 不带这个宏，走真实硬件分支。

如何新增一个硬件工具

以"控制风扇"为例，只需两步：

步骤 1：实现 handler

// ai_tools.c 里加这个函数
static char* tool_control_fan(const cJSON *args) {
    int speed = cJSON_GetObjectItem(args, "speed")->valueint;

#ifdef __PC_TEST__
    printf("  [MOCK hw_fan_set] speed=%d%%\n", speed);
#else
    /* TODO: 接 GEC6818 PWM */
#endif

    char buf[64];
    snprintf(buf, sizeof(buf), "{\"ok\":true,\"speed\":%d}", speed);
    return strdup(buf);
}

步骤 2：注册到 g_tools[]

static const ai_tool_t g_tools[] = {
    /* ... 已有的工具 ... */
    {
        "control_fan",                          // name (模型可见)
        "控制风扇转速",                       // description
        "{\"type\":\"object\",\"properties\":{"     // JSON Schema
        "\"speed\":{\"type\":\"integer\",
        "\"description\":\"转速百分比 0-100\"}"
        "},\"required\":[\"speed\"]}",
        tool_control_fan                          // handler
    },
};
重新编译 make clean && make 模型立即就能用 control_fan 了，不需要改 agent 一行代码。

static void send_btn_cb(lv_event_t *e) {
    lv_obj_t *ta = lv_event_get_user_data(e);

常见问题排查

connect failed: Connection refused
原因：Windows Ollama 没监听 0.0.0.0，只监听 127.0.0.1。
解决：set OLLAMA_HOST=0.0.0.0 后再 ollama serve。
JSON parse failed
原因：模型返回的不是合法 JSON。
排查：在 ai_agent.c 的 worker_thread 里加 printf 打印 resp，看模型实际返回了什么。常见是上下文超长被截断。
没出现 [工具调用]，只有 [最终回答]
原因：tools 字段没传成功，或模型没识别为工具调用。
排查：在 build_body() 里打印 tools_json，确认 schema 没问题。也可以用 curl 手动测一次。
模型偶尔回英文
解决：在 system prompt 加 "始终用简体中文回复。"。
cJSON.h: No such file or directory
解决：执行 make get_cjson 重新下载单文件库。
一次输入触发多次 [工具调用]
正常：这是 FC 的多轮调用。模型可能先调 read_temperature 拿数据，再调 control_led 根据温度调灯光。Agent 内部最多循环 3 次（TOOL_LOOP_MAX），防止死循环。
思考块（<think>）干扰输出
已处理：ai_agent.c 的 emit_thinking_if_any() 会自动拆分，思考内容走 AI_EVT_THINKING 事件，最终回复走 AI_EVT_ANSWER。

设计原则与边界

设计原则

01
解耦
AI Agent 和 Tools 不依赖 LVGL，可独立编译测试
02
数据驱动
新增硬件只改注册表，不改 agent 逻辑
03
事件驱动
UI 通过回调接收事件，agent 不主动碰 UI
04
双版本
PC mock 和板子真实硬件用条件编译切换
05
闭环
tool_calls 结果回传模型，模型基于真实数据生成回复

不做的事（边界）

不实现原因
流式响应（stream:true）用 stream:false 简化解析
HTTP chunked transfer-encodingOllama 在 stream:false 下不用
第三方 JSON 库依赖用 cJSON 单文件库即可
多模态（图片/音频）只做文本 + tool_calls
RAG / 向量检索工具结果就是模型的"记忆"

性能参考（GEC6818, 1GB RAM）

指标数值
单次请求耗时2-8 秒（取决于模型负载和 prompt 长度）
内存占用~5MB（agent + cJSON + HTTP buffer）
工具调用循环上限3 次（TOOL_LOOP_MAX）
对话历史上限100 轮（环形缓冲）
